# EVOLUTION_PLAN

What's deliberately out of scope for this version, and the specific trigger that would justify revisiting each decision — so scope stays deliberate rather than creeping.

## Deliberately out of scope now

**True parallel fan-out of the four external CLIs.** Current practice is sequential-with-background-polling (dispatch one, keep doing other work, check back via notification), occasionally two or three genuinely independent background calls running concurrently. Racing all four against the same question with no reconciliation process is not done.
- *Revisit trigger:* if a task genuinely needs N independent perspectives compared against each other (not just "faster"), and a clear reconciliation method is designed first — not just "run them all and see." Per the 2026-07-29 correlated-failure research below, majority vote / agreement-counting across delegates is explicitly ruled out as that method (agreement can mean shared blind spots, not confirmation) — the reconciliation method has to route through a primary source or an adversarial (not consensus-seeking) cross-check, per `QUALITY_GATES.md` Gate 5.

**A formal, automated scoring/trust system per delegate** (e.g., a maintained percentage like "Codex is right 90% of the time on X kind of claim"). Current practice treats every delegate's output with the same default skepticism regardless of track record — with one honest exception: `FAILURE_AND_RECOVERY.md` does record specific tool+claim-type failure patterns as plain-language entries once they recur (not a number, no automated lookup, just a documented "watch out for this"). That's a lightweight, hand-maintained version of exactly what this section rules out at scale — the distinction that matters is a maintained per-tool score/percentage the coordinator consults before trusting a claim (not built) versus a manually-written incident note added after the fact (already how `FAILURE_AND_RECOVERY.md` works).
- *Revisit trigger:* if the number of hand-maintained failure-pattern entries per tool grows large enough that manually cross-referencing them stops scaling — that's the point where formalizing into an actual scoring system becomes worth the overhead.

**Automating the verification step itself** (e.g., a script that auto-fact-checks delegate output). Verification currently requires the coordinator's judgment about what's worth checking and how.
- *Revisit trigger:* if a specific, mechanically-checkable claim type recurs often enough (e.g., "does this cited URL actually exist and say what's claimed") that a small verification helper is clearly worth building — build it narrowly for that claim type, not a general auto-verifier.

**Persistent memory of delegate reliability across sessions.** This skill documents patterns observed in one continuous session's history; it doesn't yet track delegate performance over time the way the coordinator's own auto-memory system (`%USERPROFILE%\.claude\projects\*\memory\MEMORY.md`, per `CONTEXT_MODEL.md`) tracks user/project facts.
- *Revisit trigger:* if a specific tool's failure mode changes materially (a Hermes update fixes the hanging issue, say) — update `FAILURE_AND_RECOVERY.md` directly rather than building tracking infrastructure for it.

## 2026-07-29 research pass — coordinator role rebalanced

The user pushed back directly: too much diagnostic legwork (VPS log-diving, registry/root-cause investigation) was being done by the coordinator itself rather than delegated, which is the "heavy lifting" this framework was supposed to keep off the coordinator's plate. Two independent delegated research passes (Codex, Antigravity) were run on the underlying multi-agent architecture question. The two arXiv papers below were verified directly via HTTP checks (both returned 200 OK with content matching the claimed titles/abstracts) rather than trusted on the delegate's word; the study citations further down were not:

- **Mixture-of-Agents** (Wang et al., ICLR 2025, arXiv:2406.04692) and **multi-agent debate** research (Du et al., arXiv:2305.14325; ICML 2024 "Should we be going MAD?") — both real, both show real gains on narrow task types but real failure modes (sycophancy, error cascades, consensus collapse) on others.
- A delegate-reported "2026 Nature Machine Intelligence study (260 configs, 6 benchmarks)" and "Anthropic's own published multi-agent research system findings" — both reportedly converge on **hub-and-spoke with centralized verification and mutation authority** outperforming unconstrained peer-to-peer agent communication, with a reported error-amplification figure (up to 17x for independent parallel agents vs. 4x for centralized). **Unlike the MoA/MAD papers above, these two were not independently confirmed by the coordinator** — no DOI, URL, or paper title was checked directly, so treat the specific numbers as delegate-reported, not verified (see `BEHAVIOR_SPEC.md`'s parallel note). The production-framework survey (AutoGen/CrewAI/LangGraph/OpenAI Agents SDK, all independently checkable real projects) is the load-bearing evidence for the hub-and-spoke decision; the study citations are corroborating, not verified.
- Correlated failure research (cross-model agreement on wrong answers 42-60% of the time) independently confirmed why "agents confirming each other's work" isn't a reliable verification mechanism — agreement isn't correctness when the errors are correlated.

**Resulting decision:** rebalance the coordinator role — diagnosis/investigation now defaults to delegation (see `WORKFLOW.md` step 2, `REQUIREMENTS.md` R1), while mutation and final verification stay centralized with the coordinator (`WORKFLOW.md` step 8, `REQUIREMENTS.md` R1) — and a defined failure loop (`WORKFLOW.md` step 8a, `REQUIREMENTS.md` R9) replaces silently absorbing a failed delegation back into solo work. Two specific proposals from the same discussion were evaluated and explicitly rejected on this evidence, not merely deferred: agents talking directly to each other to "confirm" each other's work (no reliable reconciliation mechanism given correlated failure rates), and using Codex as a prompt-router relaying between other agents (adds a P2P-style hop without the deterministic verification a hub provides). The research-split default table in `REQUIREMENTS.md` R2 was widened at the same time — Antigravity in particular was flagged as under-tested for real system/coding work relative to research, with a genuine test task called out as the way to confirm or correct that gap (not an assumption to keep carrying forward).

**Antigravity system/coding test — confirmed, same day.** Given a real task (write `sysreport.py` reading live process memory via `psutil` plus a `pytest` suite, install any missing deps itself, then actually run both and report real output), Antigravity did all of it correctly on the first pass. The coordinator independently re-read the written files and independently re-ran both commands rather than trusting Antigravity's self-report — the test results matched exactly (5/5 passed), and the live process listing was structurally identical, differing only in specific numbers because process memory is genuinely live/fluctuating between two separate runs seconds apart, not because anything was fabricated. `REQUIREMENTS.md` R2 was updated to reflect this as a verified capability, not a hopeful assumption.

## How to actually evolve this skill

When a new failure mode is discovered, or an existing documented one turns out to be stale (fixed upstream, or the workaround no longer needed), edit the relevant doc directly — `FAILURE_AND_RECOVERY.md` for failure modes, `TOOLS_AND_MCP.md` for binary paths/config that changed, `TEST_SUITE.md`'s incident table for new validating evidence. This skill is meant to stay a living reflection of real session history, not a one-time document.
